# S-101 Chart Data and Reader Contract

## Purpose and evidence

S-101 is the chart product that the chart reader must decode. In the
`S-101-Test-Datasets` submodule, relevant evidence includes:

- `S-101_1.2/000/` and `S-101_1.2/yaml/`: 32 `.000` cells and 32 YAML
  sidecars. A sidecar declares `encver: INT.IHO.S-101.1.2.0` and
  `FCVer: 1.2.0`.
- `S-101_Test_DataSets/cells/`: versioned cell directories, including update
  files.
- `S-101_Test_DataSets/exports/1.0/` and `exports/2.0/`: packaged exchange
  sets with a `CATALOG.xml`.
- S-158 and S-164 packages: additional S-101 `.000` cells and, in update
  scenarios, numbered update files.

The YAML is a useful human-readable fixture/inspection representation. It is
labelled as autogenerated from `.000`; it is not the production chart encoding
and must not become the reader's input contract.

## Container and encoding layers

Treat loading as two layers:

1. **Exchange set:** parse the S-100 `CATALOG.xml` as an exchange-catalogue
   document. Resolve its dataset, support-file, and other resource references
   relative to the exchange-set root. Keep the product specification,
   edition/version, purpose, file name, and discovery metadata associated
   with each referenced resource. Catalogues in the test repository declare
   S-101 product specification 1.1.0 in older packages; the standalone
   1.2 fixture sidecars describe S-101 encoding 1.2.0. Do not assume these
   versions are interchangeable.
2. **S-101 dataset:** decode each referenced dataset file using the S-101
   encoding version and feature catalogue identified by the package. The
   observed chart payload is ISO/IEC 8211 `.000` (and `.001`, etc. for
   updates). The S-158 `LogsDumps` XML files are human-readable dump artifacts,
   not a substitute for decoding the packaged binary cell.

## Logical dataset model

Expose a decoded dataset without discarding the distinction between feature,
information, and spatial records:

```text
S101Dataset
  identity: DatasetIdentity
  encodingVersion: ProductVersion
  featureCatalogueVersion: ProductVersion
  coordinateReferenceSystems: CoordinateReferenceSystem[]
  informationObjects: InformationObject[]
  features: Feature[]
  spatialRecords: SpatialRecord[]
  updateMetadata: UpdateMetadata?

Feature
  identity: FeatureIdentity          # includes the S-100 feature object ID (FOID)
  featureType: FeatureTypeCode        # resolve names using the matching catalogue
  primitive: Point | MultiPoint | Curve | CompositeCurve | Surface
  attributes: AttributeValue[]        # preserve code, type, and repetitions
  geometryReferences: SpatialReference[]
  associations: Association[]

SpatialRecord
  identity: SpatialIdentity
  geometry: Point | MultiPoint | Curve | CompositeCurve | Surface
```

This is the reader-facing logical shape, not a claim that these exact names
occur in the wire format. The accompanying YAML demonstrates:

- `InformationTypes`, `Points`, `Curves`, `Depths`, `Surfaces`, and `Features`
  sections;
- feature names and `Foid` values such as `1810:7702085:60000`;
- primitive and geometry references (`Prim: Surface`, `Geometry: S1302`);
- nested/repeating complex attributes represented with `id`/`parent`;
- associations with a target, association name, and role; and
- surface exterior and interior-ring references.

Keep the original coded value and its decoded value, if available. Repeating
attributes and nested attribute groups must retain their grouping and order;
do not flatten them into a single-value dictionary. Preserve unresolved
feature codes and spatial references so a missing catalogue entry is
reportable rather than silently dropped.

## Geometry and coordinate contract

- Keep geometry topology and references intact: points, multipoints, curves,
  composite curves, surfaces, exterior rings, and interior rings are distinct.
- Decode coordinates using the dataset's coordinate-reference and
  spatial-parameter metadata. Preserve coordinate dimensionality and numeric
  precision; do not treat the fixture's comma-separated latitude/longitude
  strings as the encoded representation.
- Keep vertical/depth values and their units/datum distinct from horizontal
  coordinates.
- Resolve geometry references only after the dataset records are read, so
  forward references and shared spatial records are supported.

## Base cells, updates, and reissues

Model a base cell and its update files as an ordered dataset lineage. A
`.000` file identifies a base dataset in the supplied samples; `.001` and
higher suffixes occur as numbered updates. Validate the lineage and update
sequence using catalogue metadata and S-101 update semantics before exposing
the resulting current cell. Preserve update operations and edition/update
identity while applying them; do not concatenate update records or infer
replacement semantics from filenames alone. Reissues and cancellations must
remain explicit lifecycle outcomes.

The test corpus includes valid update sequences as well as invalid sequence,
old update, reissue, cancellation, and corrupt-update cases. A reader should
return structured diagnostics for invalid inputs and must not report an
invalid sequence as a successfully loaded chart.

## Reader boundary

The implementation should provide equivalent seams to:

```text
IExchangeSetReader
  Read(exchangeSetRoot) -> ExchangeSet

IS101DatasetDecoder
  Decode(datasetStream, encodingVersion, featureCatalogue) -> S101Dataset

IS101UpdateApplier
  Apply(baseDataset, orderedUpdates) -> UpdatedS101Dataset
```

`ExchangeSet` owns catalogue metadata and resolved resource references;
`S101Dataset` owns decoded chart content; the update applier owns lineage
validation and application. Keep byte-level ISO 8211 parsing separate from
catalogue-aware feature decoding and from rendering.

## Validation checklist

- Select the decoder and catalogue from the declared product/encoding version.
- Reject malformed ISO 8211 records and report the file and record/field
  context.
- Validate required feature identity, primitive, attribute, and geometry
  references without dropping unknown extension values.
- Validate coordinate reference, dimensionality, and spatial references
  before constructing renderable geometry.
- Validate base/update identity, sequence, and lifecycle before publishing a
  current dataset.
- Compare decoded fixture output with the YAML sidecar as a test oracle only;
  the sidecar is not authoritative when it disagrees with the encoded cell.

## Open specification work

This mapping captures the repository evidence and reader boundary, not a
complete S-101 feature catalogue or exhaustive ISO 8211 field schema. Before
finalizing low-level field layouts, code-list domains, update-operation rules,
or portrayal behavior, bind them to the exact S-101 edition and encoding
specification used by each test package.
